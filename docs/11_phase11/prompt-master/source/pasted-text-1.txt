# 0. PRINCÍPIO SUPREMO

O sistema deve obedecer permanentemente:

> MODEL OUTPUT IS UNTRUSTED INPUT.

E também:

> ORCHESTRATOR DECIDES WHAT SHOULD HAPPEN.
> GOVERNANCE DECIDES WHAT MAY HAPPEN.

Nenhum LLM, Agent, Planner ou Orchestrator pode conceder a si próprio autoridade.

A autoridade pertence exclusivamente às camadas determinísticas:

* Identity;
* Tenant Boundary;
* Policy;
* Capability;
* Risk;
* Approval;
* Tool Gateway;
* Outbox;
* Execution Boundary.

# 5. CORRIJA A CADEIA DE CERTIFICAÇÃO

A auditoria encontrou um problema importante:

a certificação anterior podia apontar para um commit diferente do HEAD e havia candidato `dirty`.

Isso deve ser impossível na certificação final.

Implemente invariantes:

```text
candidate.commit == git HEAD
manifest.commit == git HEAD
phase-result.commit == git HEAD
workingTreeDirty == false
untrackedFiles == 0
```

quando estiver em modo de certificação final.

Se qualquer condição falhar:

```text
CERTIFICATION_INVALID
```

---

# 6. CERTIFICAÇÃO NÃO PODE USAR ARQUIVOS NÃO TRACKED

Todos os artefatos executáveis/testes usados para certificar devem estar reproduzíveis a partir de:

```bash
git clone
git checkout <candidate-sha>
npm ci
npm run certify
```

Nenhuma certificação pode depender de arquivos locais não commitados.

# 7. UNIFIQUE O CÁLCULO GO/NO-GO

```text
computeDecision()
```


# 12. GOAL ENGINE

Introduza `Goal` como entidade de primeira classe.

Exemplo conceitual:

```ts
interface Goal {
  id: GoalId
  tenantId: TenantId
  sessionId: SessionId
  conversationId?: ConversationId

  objective: string
  successCriteria: SuccessCriterion[]

  status: GoalStatus

  createdAt: Date
  deadline?: Date

  budget: ExecutionBudget

  correlationId: CorrelationId
}
```

---

# 13. SUCCESS CRITERIA

Goal não pode depender somente de:

```text
LLM says success
```

Critérios devem poder ser:

```text
FACT
EVENT
STATE
SEMANTIC
COMPOSITE
```

Prefira FACT/EVENT/STATE.

---

# 14. EXEMPLO

Objetivo:

```text
Agendar dermatologia para Bob amanhã à tarde.
```

Success criteria:

```text
appointment exists
patient = Bob
specialty = dermatology
date = accepted date
owner confirmation = recorded
```

Não considere tool response `200 OK` como prova suficiente.

# 20. RISK ENGINE

Crie:

```text
packages/risk-engine/
```

ou módulo equivalente.

Níveis sugeridos:

```text
R0 — informational/read-only
R1 — operational read
R2 — reversible low-risk write
R3 — meaningful external write
R4 — sensitive/high-risk write
R5 — prohibited/critical domain
```

---

# 21. SECRETARY DEFAULT POLICY

Exemplo inicial:

```text
R0 → automatic
R1 → automatic
R2 → policy-dependent
R3 → approval
R4 → human approval
R5 → deny
```

Não hardcode business policy profundamente; torne configurável/versionada.

---

# 22. CLINICAL BOUNDARY

Secretária não pode autonomamente:

```text
diagnose
prescribe
alter clinical record
release clinical result
discharge patient
make clinical decision
```

Classifique adequadamente.

---

# 23. FINANCIAL BOUNDARY

Operações financeiras sensíveis devem exigir policy/approval apropriado.

---

# 24. ADMIN BOUNDARY

Agent operacional nunca recebe:

```text
policy.admin
secret.admin
database.admin
agent.deploy
identity.admin
```

---

# 25. CAPABILITY SNAPSHOT

A capability usada na decisão deve ser registrada no execution evidence.

Mudanças futuras de policy não devem tornar auditoria histórica ambígua.

---

# 26. APPROVAL BINDING

A aprovação deve estar vinculada à ação exata.

Use canonical serialization e:

```text
payloadHash = SHA256(canonicalPayload)
```

Registre:

```text
approvalId
tenantId
operatorId
goalId
planId
stepId
action
payloadHash
policyVersion
riskLevel
expiresAt
executedAt
```

---

# 27. SINGLE-USE APPROVAL

Por padrão:

```text
one approval → one effect
```

Reuso:

```text
DENY
```

---

# 28. APPROVAL RACE SAFETY

Teste:

```text
worker A consumes approval
worker B consumes approval
```

Apenas um pode vencer.

Use transação/locking/atomic conditional update.

---

# 29. APPROVAL PERSISTENCE

Prove:

```text
request approval
restart process
approval survives
approve
execute
```

---

# 30. PAYLOAD MUTATION

Teste:

```text
approve payload A
attempt execute payload B
```

Resultado obrigatório:

```text
DENY
```

---

# 34. OUTBOX CONTINUA O BOUNDARY DE EFEITOS

# 35. EFFECT JOURNAL


# 37. COMMAND SUCCESS != GOAL SUCCESS

