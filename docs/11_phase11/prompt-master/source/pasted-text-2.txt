# CONTINUAÇÃO — PROMPT MASTER CVG-AGENT-SECRETARY-V2

## PHASE 11 — ORCHESTRATED RUNTIME & TRIPLE-AAA PRODUCTION CLOSURE

> Continuação direta do item 49 do Prompt Master. Todos os requisitos, princípios, restrições e critérios anteriores permanecem obrigatórios.

---

# 49. PERSISTÊNCIA DO ORCHESTRATOR

Crie estruturas PostgreSQL equivalentes a:

```text
orchestrator_goals
orchestrator_plans
orchestrator_steps
orchestrator_attempts
orchestrator_evaluations
```

Adapte nomes à convenção existente do repositório.

Todas devem ser:

```text
tenant-bound
auditable
versioned where appropriate
transaction-safe
recoverable
```

---

# 50. GOAL PERSISTENCE

Persistir no mínimo:

```text
goalId
tenantId
sessionId
conversationId
objective
successCriteria
status
budget
createdAt
updatedAt
deadline
correlationId
```

Não armazene apenas o prompt original.

Goal é uma entidade operacional.

---

# 51. PLAN PERSISTENCE

Persistir:

```text

goalId
tenantId
version
parentPlanId
reason
status
createdAt
```

---

# 53. ATTEMPT LEDGER

Cada tentativa deve ser registrada.

Exemplo:

```text
attemptId
stepId
workerId
leaseId
startedAt
finishedAt
outcome
errorClass
correlationId
```

Nunca sobrescrever histórico de attempts.

# 54. EVALUATION LEDGER

```text

createdAt
```

---

# 55. DURABLE STATE MACHINE

Toda transição crítica deve ser persistida atomicamente.

Não faça:

```text
memory transition
↓
later persist
```

se uma queda puder criar estado impossível.

---

# 56. OPTIMISTIC CONCURRENCY

Adicione:

```text
version
```

ou mecanismo equivalente para evitar lost updates.

Teste:

```text
worker A loads goal v7
worker B loads goal v7

A writes v8
B attempts write based on v7
```

B deve receber:

```text
CONFLICT
```

---

# 57. LEASING

Steps executáveis devem suportar lease.

Registre:

```text
leaseOwner
leaseToken
leaseUntil
```

Apenas o owner atual pode finalizar a execução.

---

# 58. FENCING TOKENS

Para operações concorrentes críticas, implemente fencing token monotônico ou mecanismo equivalente.

Objetivo:

impedir worker antigo, cujo lease expirou, de completar efeito depois de outro worker assumir.

---

# 59. WORKER CRASH RECOVERY

Prove:

```text
claim step
↓
worker crash
↓
lease expires
↓
new worker claims
↓
inspect effect journal
↓
resume safely
```

---

# 60. CRASH AFTER EFFECT

Cenário obrigatório:

```text
external effect succeeds
↓
worker crashes
↓
ack not persisted
↓
worker restarts
```

Resultado obrigatório:

```text
duplicate external effect = 0
```

---

# 61. CRASH BEFORE EFFECT

Cenário:

```text
step claimed
↓
worker crashes
↓
effect never executed
```

Outro worker deve poder continuar após lease expiration.

---

# 62. CRASH DURING EVALUATION

Evaluation deve ser reexecutável sem repetir side effect anterior.

---

# 63. ORCHESTRATOR RECOVERY

Implemente:

```text
recoverRunnableGoals()
```

ou arquitetura equivalente.

Após restart, o runtime deve descobrir trabalho pendente de forma determinística.

---

# 64. RESUME NÃO É RESTART

Não recomece Goal do zero.

Restaure:

```text
goal
active plan
completed steps
pending steps
approvals
effect journal
budget consumption
replan count
```

---

# 65. BUDGET DURABILITY

Budget consumido deve sobreviver restart.

Não permita reset de:

```text
model calls
tool calls
steps
replans
cost
```

por reinicialização do worker.

---

# 66. SCHEDULER DURÁVEL

Implemente scheduling determinístico para:

```text
WAITING_EXTERNAL
scheduled reminder
retry
deadline
approval expiration
```

Não use LLM como scheduler.

---

# 67. SCHEDULER RECOVERY

Após restart:

```text
due jobs
```

devem ser recuperados.

---

# 68. CLOCK

Use clock injetável nos testes.

Produção usa clock real controlado pelo runtime.

Nunca espalhe `Date.now()` arbitrariamente por regras de domínio quando puder usar abstraction.

---

# 87. PHASE 11.9 — LEGACY RUNTIME ELIMINATION

---

# 88. ZERO BYPASS

Objetivo:

```text
external effects bypassing governed runtime = 0
```

---

# 89. KERNEL COMO ÚNICO RUNTIME DE PRODUÇÃO

Produção deve usar:

```text
CVG_WORKER_RUNTIME=kernel
```

ou equivalente.

Legacy runtime:

```text
test-only
migration-only
removed
```

Não mantenha dois runtimes de produção equivalentes.

---

# 90. LEGACY DEPRECATION

Se não puder remover imediatamente:

* marque deprecated;
* bloqueie em production;
* teste o bloqueio;
* crie migration path;
* registre backlog.

---

# 91. DIRECT HTTP AUDIT

Procure chamadas HTTP externas fora dos adapters/gateways permitidos.

Falhe architectural test quando aparecer bypass.

---

# 92. ARCHITECTURE TESTS

---

# 109. PLAN INJECTION

```text

```

---

# 110. CAPABILITY ESCALATION

Replanner não pode adicionar capability que o agent não possui.

---

# 111. RISK DOWNGRADE ATTACK

---

# 112. APPROVAL DOWNGRADE ATTACK

---

# 113. TENANT IMMUTABILITY

```text

```

```text

```

---

# 114. CROSS-TENANT ADVERSARIAL SUITE

```text

execute
evaluate
resume
```

---

# 115. AUTHORIZATION TOCTOU
